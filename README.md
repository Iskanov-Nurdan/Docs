# Веб-редактор документов

Совместная работа с текстовыми документами: одновременное редактирование,
комментарии, предложения правок, история версий, права доступа, импорт и экспорт.

## Что уже работает

**Ядро** — то, ради чего всё затевалось (разделы 103–107 ТЗ):

- редактор на TipTap/ProseMirror: документ хранится деревом узлов, а не строкой HTML;
- совместное редактирование через Yjs (CRDT): правки двух человек в один абзац
  сливаются, не затирая друг друга;
- WebSocket на Django Channels: приращения, курсоры, присутствие участников;
- работа без сети: правки копятся в IndexedDB и уходят на сервер при восстановлении связи;
- автосохранение — отдельной кнопки нет.

**Учётные записи**: регистрация с подтверждением почты, вход, продление сессии,
восстановление и смена пароля, профиль, язык, тема, настройки редактора.

**Документы**: создание, папки, избранное, корзина с восстановлением,
полнотекстовый поиск PostgreSQL, копирование, сортировка, вид сеткой и списком.

**Доступ**: роли владельца, редактора, комментатора и читателя; доступ по ссылке;
запрет скачивания, копирования и печати. Проверка одна на всё приложение —
`AccessService.require`.

**Совместная работа**: комментарии с ветками ответов, реакции, задачи с исполнителем,
предложения правок с принятием и отклонением, уведомления в приложении и по почте.

**История версий**: снимки по расписанию и по требованию, просмотр и восстановление —
без удаления предыдущих версий.

**Файлы**: загрузка изображений с проверкой настоящего типа, импорт DOCX и TXT,
экспорт в PDF, DOCX, TXT, HTML, RTF и ODT — в фоне через Celery.

**Публикация**: документ отдаётся по адресу `/published/{id}` снимком, чтобы черновые
правки не уходили читателям сразу.

## Чего ещё нет

Против списка из ТЗ не сделаны: колонтитулы и номера страниц, сноски, оглавление
в интерфейсе (данные для него сервер уже отдаёт), закладки, smart chips, выпадающие
списки, готовые блоки, редактор формул, линейка, галерея шаблонов, панель комментариев
в интерфейсе редактора, режим Suggesting на стороне редактора (API готов),
административная панель со статистикой, мобильная раскладка редактора.

Порядок работ — по разделу 106 ТЗ. Ядро (фазы 1–5) закрыто, дальше идут
фазы 6–16.

## Запуск

Нужен Docker с плагином Compose.

```bash
cp .env.example .env
# задайте POSTGRES_PASSWORD и DJANGO_SECRET_KEY
docker compose up -d --build
```

Через минуту-две:

- приложение — http://localhost:8080
- API — http://localhost:8080/api/
- админка — http://localhost:8080/django-admin/

Первый администратор:

```bash
docker compose exec api python manage.py createsuperuser
```

## Разработка

```bash
docker compose logs -f api          # журнал бэкенда
docker compose logs -f worker       # фоновые задачи
docker compose exec api python manage.py makemigrations
docker compose exec api python manage.py migrate
docker compose exec frontend npm run typecheck
```

Фронтенд можно поднять и без контейнера:

```bash
cd frontend && npm install && npm run dev
```

### Как хранится документ

Содержимое живёт в двух видах:

- **`ydoc_state`** — двоичное состояние Yjs. Оно главное при совместной работе:
  только CRDT сливает правки двух людей в один участок текста без потерь.
- **`content`** — то же дерево узлов ProseMirror в JSON. Нужно всему, что работает
  без редактора: поиск, экспорт, печать, версии, публикация.

Сервер не разбирает приращения Yjs — он складывает их в журнал и раздаёт остальным.
Свёрнутое состояние присылает та вкладка, где документ открыт; после этого журнал
очищается. Так сервер обходится без реализации CRDT на Python, ничего не теряя.

Хранить один HTML и перезаписывать его целиком нельзя: при одновременной правке
победил бы тот, кто сохранил последним.
